我最近看 Codex 的上下文压缩机制，最大的感受不是“这个机制很巧”，而是：它很适合桌面 Agent，但不一定适合 C 端 Agent。

桌面 Agent 的上下文，本质上是一个工作现场。

用户给了需求，Agent 读文件、改代码、跑测试、失败、修复、再继续。它需要知道刚刚做过什么、哪些方案试过、哪些文件改了、还有哪些待办。上下文快满的时候，把历史压缩成一份交接摘要，是合理的。

但 C 端 Agent 不一样。

C 端用户不是在和 Agent 共同维护一个工程现场。他可能只是问一个问题、做一次练习、上传一份内容、看一次反馈，或者让系统推荐下一步。这里真正重要的不是“尽量保存完整对话”，而是“这次回答需要哪些用户信息”。

如果把桌面 Agent 的机制直接搬到 C 端，会出问题。

## 桌面 Agent 的上下文是工作流，C 端 Agent 的上下文是产品判断

Codex 这类桌面 Agent 的压缩机制，大致可以理解成：

把历史对话和摘要指令一起发给 LLM，让模型生成结构化摘要，比如当前进度、关键决策、待办事项、重要上下文。然后保留最近一段用户消息，系统指令重新注入，压缩摘要作为交接信息继续进入下一轮。

这个设计背后的假设是：任务是连续的，历史是有价值的，Agent 要接着干。

这在编程场景里很自然。

但 C 端产品里，很多请求并不需要完整历史。用户问一个独立问题，系统不需要过去几十轮聊天。用户做一次批改，模型主要需要当前内容和评分标准。用户要学习建议，系统更需要结构化学习状态，而不是聊天全文。

桌面 Agent 的目标是“不断线”。

C 端 Agent 的目标是“回答得刚好”。

这两个目标会导向完全不同的上下文机制。

## 如果直接照搬，第一件事是成本失控

现在很多模型窗口已经很大，256K、1M 都不稀奇。于是很容易产生一种幻觉：既然窗口够大，那就多塞一点历史，体验会更好。

但大窗口不是免费的。

如果每次请求都接近 256K token，C 端产品会很快遇到费用问题。更麻烦的是，这种费用增长不是线性的产品价值增长。

用户可能只是问了一个很短的问题，但后端为了“记忆”，把大量会话历史、摘要、系统信息、用户历史记录都塞进去。模型确实看到了更多内容，但用户未必得到更好的回答。

这就是 C 端上下文最危险的地方：

你花了很多 token，用户没有感知到对应价值。

桌面 Agent 的长上下文常常有明确收益，因为它要继续完成复杂任务。C 端的大多数请求没有这个收益密度。

## 第二件事是并发被长请求拖垮

长上下文请求不仅贵，还慢。

LLM API 通常有并发限制、速率限制、token 速率限制。一个 256K token 的请求，会占用更长时间，也会消耗更多 provider 侧的处理资源。

在 C 端，这会变成一个稳定性问题。

假设同时在线用户很多，每个请求都带大量历史。即使 QPS 不高，长请求也会占住并发槽。新的请求排队，用户等待时间变长，失败率上升。最后看起来像是“模型不稳定”，实际是上下文策略太重。

桌面 Agent 可以容忍等待。

C 端用户不太会。

开发者等 Agent 多思考几秒，可能觉得合理。普通用户等一个日常问题等十几秒，只会觉得产品慢。

## 第三件事是服务器内存压力被放大

还有一个容易被忽略的问题：上下文不是直接从数据库飞到模型里的。

中间要查数据库、反序列化、组装消息、拼 prompt、记录日志、做 token 估算、进入请求对象。每个并发请求都会在应用服务器内存里形成一份上下文。

如果策略是“根据 session_id 全表查询”或者“尽可能多拿历史”，高并发时内存会被放大。

PostgreSQL 保存完整历史没有问题。

问题是每次请求都把大量历史搬到内存里。

C 端系统的默认策略应该是少取、准取、按预算取，而不是全取之后再压缩。

## 第四件事是回答会被旧上下文污染

上下文越多，不一定越聪明。

C 端用户的意图经常切换。上午问写作，下午问阅读；今天问备考计划，明天问一个独立知识点。如果系统默认带大量历史，模型可能会把旧信息误认为当前任务的一部分。

这会产生一种很微妙的体验问题：

用户明明问的是一个简单问题，Agent 却不断提起以前的目标、以前的练习、以前的错误。

用户想要当前答案，Agent 却表现得像在延续一个并不存在的任务。

这不是记忆好，而是上下文边界差。

桌面 Agent 里，任务通常是连续的，旧上下文大多有用。C 端里，用户场景是跳跃的，旧上下文经常需要被隔离。

## 第五件事是“记忆”会变得不可控

如果把聊天历史和摘要当成主要记忆来源，C 端 Agent 很容易变成一个黑箱。

它为什么认为用户薄弱？

为什么推荐这个任务？

为什么记住这件事而忘了另一件事？

用户能不能修改？能不能删除？

Codex 的摘要是为了交接工作，不是为了构建用户画像。它不需要让用户管理“我被记住了什么”。

但 C 端需要。

C 端记忆应该尽量结构化：目标、水平、偏好、薄弱项、学习进度、历史任务。这些信息应该来自数据库里的业务事实，能解释，能更新，能删除。

如果只靠 LLM 摘要长期滚动，系统会越来越难解释，也越来越难纠错。

## Claude / Codex 式机制不是错，而是场景假设不同

这不是说 Codex 或 Claude Code 的机制不好。

恰恰相反，它们的机制对桌面 Agent 是合理的。因为桌面 Agent 的核心是长任务执行。上下文像施工现场，压缩像交接班记录。只要交接信息足够好，Agent 就能继续往前推进。

但 C 端 Agent 的核心不是交接班。

它更像一个有记忆的服务系统。每次请求都要判断：当前场景是什么？用户需要个性化吗？需要哪一类历史？最多能花多少 token？哪些信息会干扰当前回答？

所以 C 端不能只有“上下文压缩器”。它更需要“上下文调度器”。

## 真正困难的是按场景设计上下文

这件事不能靠一套通用规则一次性解决。

C 端 Agent 的上下文机制，必须根据具体场景来设计。普通问答、练习批改、学习规划、错题复盘、陪练对话，它们需要的上下文完全不同。

有些场景几乎不需要历史。

有些场景只需要最近几轮对话。

有些场景需要当前任务材料。

有些场景需要用户长期学习状态。

有些场景需要从数据库里检索相关记录。

问题不是“要不要记忆”，而是：

这个场景下，用户到底期待 Agent 记住什么？

哪些信息会提升回答质量？

哪些信息只是增加成本？

哪些旧上下文会干扰当前任务？

为了这次体验，最多值得花多少 token？

这需要既懂用户，也懂成本。

只懂模型的人，容易把上下文越堆越长。

只懂成本的人，容易把 Agent 做成没有记忆的问答工具。

真正难的是在中间找到平衡：让用户感觉它懂我，但不要每次请求都背着一整本历史聊天记录。

这也是 C 端 Agent 上下文设计最需要反复打磨的地方。

不是先设计一个宏大的记忆系统，然后期待所有场景都适配它。更现实的路径是：从具体场景开始，观察用户真正怎么问、真正需要什么，然后一点点调整上下文层级、token 预算、记忆写入规则和检索策略。

这个过程很工程，也很产品。

## C 端更适合按场景调度记忆

我现在更倾向于把 C 端上下文拆成几层。

第一层是当前输入。

用户这次说了什么、上传了什么、正在操作什么。

第二层是当前任务。

比如当前题目、当前作文、当前练习、当前批改结果。

第三层是短期会话。

只保留最近少量对话，用来处理“刚才那个”“继续”“换一种说法”。

第四层是用户状态。

目标、水平、薄弱项、偏好、近期进度。

第五层是场景相关历史。

只有当当前问题需要时，才从数据库里检索相关记录。

这套机制不是等窗口快满了再压缩，而是从请求开始就做预算。

每次请求都应该先回答几个问题：

这次是否需要历史？

需要哪种历史？

最多带多少？

旧上下文会不会干扰？

这次调用值不值得花更多 token？

这比“90% 窗口触发压缩”更适合 C 端。

## 更实际的设计原则

如果要把 Agent 做成 C 端产品，我会先设几条硬规则。

第一，不默认使用大窗口。

大窗口是兜底能力，不是日常策略。

第二，不默认全量查会话。

数据库保存完整历史，但请求只取必要部分。

第三，不把聊天摘要当成唯一记忆。

长期记忆应该来自结构化业务数据。

第四，不同场景使用不同上下文预算。

普通问答、练习批改、学习规划、错题复盘，不应该共用一套 prompt 拼接规则。

第五，LLM 调用要有成本和并发保护。

包括单次最大输入 token、用户级调用频率、队列、降级策略、预算统计。

第六，旧上下文要能被拒绝。

不是所有历史都该进入当前回答。很多时候，少带上下文比多带上下文更准确。

第七，把上下文机制当成产品能力持续打磨。

它不是一次架构设计就结束的东西，而是要随着真实用户行为不断调整。

## 最后的判断

桌面 Agent 的上下文机制解决的是：

如何让 Agent 在长任务里不断片。

C 端 Agent 的上下文机制解决的是：

如何在每次请求里，只使用对用户真正有价值的信息。

这两件事看起来都叫“上下文”，但工程设计完全不同。

Codex 式压缩可以作为参考，但不能作为 C 端默认方案。直接照搬，后果大概率是成本更高、延迟更长、并发更脆、内存压力更大，甚至回答还更容易被旧历史污染。

C 端 Agent 真正需要的不是更大的上下文窗口，而是更克制的上下文选择能力。

不是记得越多越好。

是每次只记得该记的。

而这件事没有捷径。它需要在真实场景里一轮一轮打磨：既要理解用户想要什么，也要控制每次调用的成本，还要保证 Agent 的效果真的变好。

这也是我接下来真正要做的事情。
