过去两年，我们使用 AI 编程工具的方式，很像在旁边带一个新同事。

你写一句 Prompt，它回一段代码。你看一眼，再补一句。它改一点，你再指出哪里不对。整个过程里，Agent 很强，但它仍然是被你牵着走的工具。

Addy Osmani 在《[Loop Engineering](https://addyosmani.com/blog/loop-engineering/)》里讲的变化，是这个牵引关系正在反过来。

不是你一轮一轮提示 Agent，而是你设计一个循环，让系统自己发现任务、分发任务、执行任务、检查任务、记录状态，然后再决定下一步该做什么。

这听起来像自动化，但它比普通自动化更靠近工程管理。

我更愿意把 Loop Engineering 理解成一句话：

**Prompt 工程是在写一次请求，Loop Engineering 是在设计一套会持续工作的开发流程。**

## Prompt 的问题不是不够聪明，而是太依赖人

很多人对 AI 编程的第一反应，是继续优化 Prompt。

“帮我重构这个模块。”

“严格遵守项目规范。”

“先阅读上下文，再给出方案。”

“写完后运行测试。”

这些当然有用。但问题是，每一次你都要重新启动这套流程。

你要提醒它读项目规范，要提醒它检查测试，要提醒它别改无关文件，要提醒它输出总结。你像一个永远在线的调度器，负责把上下文、目标、边界和验收标准不断塞给模型。

这就是 Prompt 工程的天花板：

它提高了单次对话的质量，但没有降低你作为操作者的负担。

Loop Engineering 想解决的不是“这一轮怎么提示得更好”，而是“这些提示为什么每次都需要我来发”。

## 一个 Loop 本质上是小型开发系统

Addy 把一个 Loop 拆成几个关键部分：自动化、worktree、skills、plugins/connectors、sub-agents，以及外部状态记录。

这些东西单独看都不新。

自动化负责定时发现问题，比如每天检查 CI 失败、issue 变化、最近提交。

worktree 负责隔离并行任务，避免多个 Agent 同时改同一份代码。

skills 负责保存项目知识，避免每次都从零解释团队约定。

connectors 负责接入真实工具，比如 GitHub、Linear、Slack、数据库。

sub-agents 负责分工，一个写代码，另一个审查。

状态文件或任务系统负责记住这次做了什么，下次应该从哪里继续。

真正有意思的是，把它们连起来之后，Agent 就不再只是“会写代码的聊天窗口”。

它开始像一个持续运行的小型开发系统。

比如一个很实际的 Loop 可以是这样：

每天早上自动扫描仓库，读取昨天失败的 CI、最近新增 issue、过去一天的 commit。它用一个 triage skill 判断哪些问题值得处理，把结果写进一个 markdown 状态文件。对确定要处理的问题，它开一个独立 worktree，让一个 Agent 尝试修复，再让另一个 Agent 根据项目规则和测试结果做 review。能自动开 PR 的就开 PR，不能处理的才进入人工 triage。

你并没有逐步提示每个 Agent。

你设计的是这个循环本身。

这就是控制权的移动。

## Skills 的价值，是把隐性判断从人脑里搬出去

我觉得这篇文章里最容易被低估的是 skills。

很多人会把 skill 理解成“更长的 Prompt 模板”。但它更重要的作用，是把项目里的隐性判断固化下来。

比如：

这个项目为什么不用某个库。

哪些目录不能随便重构。

新增接口必须补哪些测试。

前端组件有什么设计约束。

CI 失败时应该先看哪几个日志。

代码注释应该写到什么程度。

这些东西通常存在于老同事脑子里、历史 PR 里、某次事故复盘里。人类靠记忆和团队文化传递，Agent 则每次冷启动。

如果没有 skill，Loop 每跑一次都要重新猜一遍项目意图。

如果有 skill，Loop 才有可能越跑越稳定。

这也是我觉得 Loop Engineering 比 Prompt Engineering 更接近软件工程的地方。

Prompt 解决表达问题。

Skill 解决组织记忆问题。

Loop 解决持续执行问题。

## Sub-agent 最重要的不是并行，而是制衡

很多人一听 sub-agent，会先想到“并行加速”。

一个 Agent 看前端，一个 Agent 看后端，一个 Agent 写测试。确实可以。但在真实工程里，我觉得 sub-agent 更重要的价值不是多快，而是谁来检查谁。

写代码的 Agent 很容易相信自己的方案。它会解释得很顺，补丁也看起来合理，但里面可能藏着边界问题、错误假设、测试遗漏，甚至只是把复杂度换了个地方。

所以一个可靠的 Loop 里，maker 和 checker 最好分开。

一个 Agent 负责实现。

另一个 Agent 负责挑错。

必要时第三个 Agent 只看安全、性能或兼容性。

这不是为了仪式感，而是因为无人值守的循环最怕“自我确认”。

当 Loop 开始自动运行时，“看起来完成了”会变成非常危险的状态。你需要一个独立的检查者，让完成条件不只是实现者自己的判断。

当然，这也有代价。

更多 Agent 意味着更多 token、更多时间、更多中间状态，也可能带来更多协调成本。

所以 sub-agent 不应该随便堆。它适合用在高风险环节：核心逻辑、权限、安全、数据迁移、复杂重构、用户可见行为变化。

便宜的地方让一个 Agent 做。

贵的地方才值得请第二双眼睛。

## Worktree 解决文件冲突，但解决不了人的 review 带宽

Loop 一旦能并行，就一定会遇到隔离问题。

两个 Agent 同时改一个仓库，如果没有 worktree，很快就会互相踩文件。git worktree 的价值很直接：每个任务一个独立目录、独立分支，彼此不污染。

但这只解决机械冲突，不解决认知冲突。

你可以同时跑五个 Agent，让它们各自开五个 PR。问题是，你真的有能力理解这五个 PR 吗？

AI 编程最容易制造一种错觉：代码产出速度提高了，工程能力也提高了。实际上，产出速度只是系统的一半。另一半是理解、验证和承担后果。

Loop 可以扩大执行能力，但你的 review 带宽仍然是瓶颈。

如果你不读代码、不跑测试、不理解改动，只是把 Agent 产出的东西合进去，那 Loop 不是杠杆，而是债务机器。

## Loop 不会替你保持工程判断

这篇文章最后的提醒很重要：Loop Engineering 不是让工程师退出现场。

恰恰相反，它要求工程师更清楚自己在设计什么。

同样一个 Loop，两个人用会得到完全不同的结果。

一个人用它处理自己已经理解的重复工作，把时间省下来做更难的判断。

另一个人用它逃避理解，把看不懂的任务交给 Agent，然后接受它给出的任何答案。

表面上，他们都在“自动化开发”。

结果可能完全相反。

这也是 Loop 比 Prompt 更难的地方。

Prompt 写得不好，通常只是这一轮结果差。

Loop 设计得不好，会稳定地产生差结果。

它会每天运行。

它会不断提交。

它会把你的错误假设规模化。

所以真正的问题不是“要不要用 Loop”，而是你有没有能力定义一个值得持续运行的循环。

## 我会从很小的 Loop 开始

如果让我现在在项目里引入 Loop Engineering，我不会一上来就做全自动修复、全自动 PR、全自动合并。

我会从三个低风险场景开始。

第一，自动发现问题。

比如每天总结 CI 失败、最近 issue、潜在重复 bug。先让 Loop 做观察者，不让它直接改代码。

第二，自动整理上下文。

比如把某个模块的近期变更、相关测试、已知约束写进状态文件。它不替我决策，只减少我进入问题的成本。

第三，自动做第二意见。

比如我写完代码后，让一个 review agent 根据项目 skill 检查风险、遗漏测试和不一致的实现。

这三个场景的共同点是：

Loop 提供判断材料，但最终控制权还在人这里。

等这些环节稳定之后，再考虑让它进入更主动的执行阶段。

## Prompt 没有消失，只是变成了系统的一部分

Loop Engineering 并不意味着 Prompt Engineering 过时了。

Prompt 仍然重要，只是它不再只是聊天框里那一句话。它变成了 automation 的任务描述、skill 的项目约束、sub-agent 的角色定义、goal 的完成条件、reviewer 的检查标准。

过去我们优化的是一次对话。

现在我们优化的是一条工作流。

这也是 AI 编程接下来真正值得关注的地方：不是哪个模型又多写对了几个函数，而是谁能把模型放进一个更可靠的工程系统里。

我的判断是，未来会写 Prompt 的人很多，会设计 Loop 的人少一些。

因为 Loop 需要的不只是表达能力，还需要工程直觉：

哪些事情可以自动化。

哪些地方必须隔离。

哪些判断要写成 skill。

哪些结果需要第二个 Agent 检查。

哪些步骤永远不能跳过人工确认。

AI 可以替你执行很多步骤。

但它不能替你决定，什么样的执行系统是值得信任的。

所以可以开始设计 Loop。

但别把自己从工程里删掉。

真正的目标不是成为按下按钮的人，而是成为设计这套按钮背后系统的人。
